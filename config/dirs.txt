# Directories created by run.sh, one per line. Variables come from
# config/site.env.
#
# A line may carry a GROUP: prefix, which decides *when* in the run it is
# created. Anything living on a filesystem that gets mounted must not be
# created before that mount, or it lands on / and the mount then shadows
# it -- invisible, and quietly filling the root disk.
#
#   (none)    $DOCKER_ROOT and $CONFIG. Always on the root filesystem,
#             so created immediately.
#   DATA:     created only once $DATA is mounted, or once fstab confirms
#             it was never meant to be a separate disk.
#   NAS:      created after the NFS export is mounted. Skipped entirely
#             in --minimal, which exits before that step.
#
# A line may carry an optional trailing owner field:
#
#   uid:gid   override the default ownership of $PUID:$PGID, for images
#             that run as a fixed uid of their own
#   -         create it but never chown it, and never check it, for
#             directories whose ownership belongs to the service rather
#             than to us
#
# Ownership is applied on creation only. An existing directory with
# unexpected ownership is reported, not changed.
#
# A service running as root is NOT by itself a reason for `-`. Root
# writes happily into a $PUID-owned directory and leaves the ownership
# alone: caddy, jellyfin and vaultwarden all run as root and are all
# $PUID:$PGID on bmo. Only two things actually produce a directory whose
# owner is not ours to expect --
#
#   1. a service that chowns its own data directory to its own uid
#      (the database engines: immich/database is 999:1000, romm/mysql
#      is 999:999)
#   2. one Docker auto-created as root:root before this file covered it,
#      which is never corrected afterwards because ownership is applied
#      on creation only (gluetun, the romm subdirectories)
#
# Those get `-`. Everything else keeps the default, and a mismatch there
# is a real finding.
#
# To settle what an image actually does, ask the disk, on the host:
#
#   find $CONFIG -maxdepth 2 -type d -printf '%U:%G  %p\n' | sort -k2
#
# Do NOT use `docker exec <c> id -u` for this. It reports the uid of the
# exec process, which for every s6-overlay image (all the lscr.io ones,
# and tomsquest/docker-radicale) is root -- s6 starts as root and only
# then drops the application to PUID. radicale reports uid 0 that way
# while its data genuinely needs 2999:2999. Ownership on disk is what
# the container actually did, and it is the thing this file describes.
#
# Every path that a compose file bind-mounts belongs here. Docker creates
# a missing bind-mount source itself, as root:root, which any container
# running as a non-root user then cannot write to.
